## The Prompt

The following prompt was used to generate the API scaffold for the Task Manager system.
This reflects the actual prompt strategy used during development — broken into focused,
layered requests rather than one large prompt, which produces more reliable and
reviewable output.

```
Generate a .NET 8 Web API using Clean Architecture with the following requirements:

Domain layer:
- TaskItem entity: Id (Guid), Title (string), Description (string),
  Status (enum: Todo/InProgress/Done), DueDate (DateTime), UserId (Guid), CreatedAt (DateTime)
- User entity: Id (Guid), Name (string), Email (string), PasswordHash (string), CreatedAt (DateTime)
- No dependencies on any other layer or NuGet package

Application layer:
- ITaskRepository: GetAllByUserAsync(Guid userId), GetByIdAsync(Guid id),
  CreateAsync(TaskItem), UpdateAsync(TaskItem), DeleteAsync(Guid id)
- IUserRepository: GetByEmailAsync(string email), CreateAsync(User), GetByIdAsync(Guid id)
- TaskService with validation: title required (max 200 chars), DueDate must be in future,
  status must be valid; throw ArgumentException on violations
- AuthService: register with BCrypt password hashing, login with JWT generation;
  throw ValidationException on invalid input or duplicate email

Infrastructure layer:
- TaskRepository and UserRepository using Microsoft.Data.SqlClient (ADO.NET only)
- No Entity Framework, no Dapper, no MediatR
- Parameterized queries only, manual SqlDataReader mapping

WebApi layer:
- TaskController: full CRUD under [Authorize], extract userId from JWT NameIdentifier claim
- AuthController: POST /register, POST /login, GET /me (authorized)
- One public endpoint: GET /api/tasks/public (no auth required)
- Return ProblemDetails on validation errors (400), 403 on ownership violations, 404 on not found

Tests:
- xUnit + Moq + FluentAssertions
- TaskService: empty title, past DueDate, valid input calls repository, user isolation,
  delete ownership check
- AuthService: null user, invalid email, short password, duplicate email,
  wrong credentials, valid login returns token
```

## Representative Sample of AI Output

The following is the AuthServiceTests.cs file generated by the Gemini agent (via GitHub
Copilot), using the existing TaskServiceTests.cs as a reference and the context.md
architectural guide as grounding:

```csharp
public class AuthServiceTests
{
    private readonly Mock<IUserRepository> _userRepositoryMock = new();
    private readonly Mock<IConfiguration> _configurationMock = new();

    private AuthService CreateService() => new(_userRepositoryMock.Object, _configurationMock.Object);

    [Fact]
    public async Task RegisterAsync_ShouldThrowValidationException_WhenUserIsNull()
    {
        var service = CreateService();

        await FluentActions.Invoking(() => service.RegisterAsync(null!, "password123"))
            .Should().ThrowAsync<ValidationException>()
            .WithMessage("User is required.");
    }

    [Theory]
    [InlineData(null)]
    [InlineData("")]
    [InlineData("   ")]
    public async Task RegisterAsync_ShouldThrowValidationException_WhenEmailIsInvalid(string? email)
    {
        var service = CreateService();
        var user = new User { Email = email!, Name = "Test User" };

        await FluentActions.Invoking(() => service.RegisterAsync(user, "password123"))
            .Should().ThrowAsync<ValidationException>()
            .WithMessage("Email is required.");
    }

    [Fact]
    public async Task LoginAsync_ShouldReturnToken_WhenCredentialsAreValid()
    {
        var password = "validPassword123";
        var user = new User
        {
            Id = Guid.NewGuid(),
            Email = "valid@test.com",
            PasswordHash = BCrypt.Net.BCrypt.HashPassword(password),
            Name = "Test User"
        };
        _userRepositoryMock.Setup(x => x.GetByEmailAsync(user.Email)).ReturnsAsync(user);
        _configurationMock.Setup(x => x["Jwt:Secret"])
            .Returns("this-is-a-very-long-secret-key-32-chars-min");

        var service = CreateService();
        var token = await service.LoginAsync(user.Email, password);

        token.Should().NotBeNullOrWhiteSpace();
    }
}
```

## How I Validated the AI's Output

### What I checked before accepting any generated code

**1. Dependency direction**
The first thing I verify in every generated file is whether imports and dependencies
point inward (toward Domain) and never outward. The AI occasionally generates
infrastructure references inside the Application layer — a Clean Architecture violation
that gets caught immediately by reading the `using` statements.

**2. ADO.NET compliance**
The test explicitly forbids Entity Framework, Dapper, and MediatR. On the first
infrastructure generation attempt, the AI defaulted to EF Core internally despite
the prompt saying otherwise. I caught this by checking the `.csproj` packages and
the repository implementation — it was using `DbContext` underneath. I re-prompted
with a stricter constraint and reviewed the `SqlConnection`/`SqlCommand` usage manually.

**3. User isolation**
The initial `GetAllAsync` implementation returned all tasks in the database without
filtering by `UserId`. This is a security boundary, not just a functional bug. I
identified it by tracing what the controller would pass to the service vs. what the
repository query actually filtered on. Added the `WHERE UserId = @UserId` clause
and a corresponding ownership check in `DeleteAsync`.

**4. JWT secret management**
Generated code had the JWT secret hardcoded as a string literal in `AuthService`.
Moved it to `IConfiguration["Jwt:Secret"]` with the actual value in
`appsettings.Development.json` (excluded from version control via `.gitignore`).

**5. Exception types**
The AI mixed `Exception`, `ValidationException`, and `ArgumentException` inconsistently
across services. Standardized to `ArgumentException` for input validation in
`TaskService` and `ValidationException` for business rule violations in `AuthService`,
making the controller exception handling predictable and consistent.

## How I Handled Edge Cases, Auth, and Validations

### Authentication
- Chose JWT Bearer over ASP.NET Identity — Identity adds role pipelines, cookie
  management, and EF Core dependency that aren't justified for this scope.
- Token contains `userId` as a `NameIdentifier` claim, extracted in controllers via
  `User.FindFirstValue(ClaimTypes.NameIdentifier)`.
- Passwords hashed with BCrypt (BCrypt.Net-Next 4.0.3) — never stored in plain text,
  never logged.
- JWT secret stored only in `appsettings.Development.json`, which is in `.gitignore`.

### Validations (Application layer, not controller)
Business rules live in the service layer, not in controllers or DTOs, so they are
testable without HTTP context:
- Title: required, max 200 characters
- DueDate: must be strictly in the future on creation
- Status: must be a valid `TaskStatus` enum value
- Email: required, must be unique across users
- Password: minimum 8 characters

### Edge cases tested
- Null and whitespace inputs (via `[Theory]` + `[InlineData]`)
- Duplicate email registration
- Login with non-existent email
- Login with wrong password (BCrypt mismatch)
- Delete of a task belonging to a different user (ownership enforcement)
- DueDate in the past on create

## Note on Session History

During development, GitHub Copilot free tier was used extensively for scaffolding
and iteration. The free tier does not persist chat history across sessions — prompts
and responses from earlier sessions were lost when the IDE was closed.

The prompt documented above reflects the actual strategy used: layered, specific
prompts focused on one architectural concern at a time, rather than a single large
prompt. This approach produces more reviewable output and makes it easier to catch
violations before they propagate across layers.

The Gemini-generated AuthServiceTests.cs shown above is the one verifiable AI
interaction with a preserved output, and serves as a concrete example of the
prompt → output → review → accept cycle applied throughout the project.

## Takeaway

AI tools are effective for:
- Generating boilerplate that matches a well-defined architecture
- Remembering syntax and API signatures in less-used frameworks
- Producing test skeletons when given existing tests as examples

Critical thinking is required for:
- Security boundaries (user isolation, secret management)
- Dependency direction in layered architectures
- Exception consistency across layers
- Verifying that explicit constraints (no EF, no Dapper) are actually honored
  and not quietly bypassed in generated output
